## Patch 0.3.23: per-recipient dispatch allowance and three-zone admin replies

Admin replies use the admin's three zones: **Agents-Zone** (every step, with a time only from a real clock),
**Result-Zone** (key-first bullets) and **Admin-Zone** (the Conclusion line and the eight sections), as in
i-have-asd-ste100 0.11.0. Dispatch change:

Queued native sends to different members now run concurrently. Each eligible recipient has an independent
20-message selection bound. Direct messages for that recipient precede FYI copies, with FIFO preserved inside
each class. There is no room-wide budget or direct/FYI phase barrier: one busy inbox cannot consume another
member's allowance. Dispatch still waits for every selected recipient queue before its next tick. Unexpected
failures are raised after the selected queues settle, so unfinished attempts remain recoverable as unknown.

## Patch 0.3.25: room modes, per-member effort and `/agent-room:init`

Admin decisions of 2026-10-03. New rooms start in `pair` mode: CLAUDE_01 (CLAUDE_WORKER, requested Opus 5.5 medium)
and CODEX_01 (CODEX_WORKER, Sol 6.1 medium). `advisors` is the four-member room: CLAUDE_01 Sonnet 5.5 xhigh,
CODEX_01 Luna 6 xhigh, CLAUDE_EXPERT Opus 5.5 xhigh, CODEX_EXPERT Sol 6.1 xhigh. This supersedes DEC-021's
four-member default for new rooms only. Stored rooms in the legacy modes `default` and `full` keep all four members
with the advisors settings. `agent-room mode [pair|advisors]` shows or switches the mode now: open tasks and reviews
of leaving members must be handed off first; a running room restarts its workers on their exact sessions with the
new settings and keeps queued messages; leaving members stop and joining members start. `agent-room effort [LEVEL]
[--member NAME | --all] [--clear]` shows or sets each room-controlled member's requested effort (low, medium, high,
xhigh, max). The first effort level observed after init is recorded as a baseline and changes nothing. When the gateway session's effort later changes (hook field `effort.level` or `$CLAUDE_EFFORT`, read at the
admin's next prompt), every room-controlled member follows it and manual overrides are cleared. Codex members use
new settings on their next turn. A running Claude worker shows `settings_pending_restart` and gets them when it next
resumes: its settings file now requests `model` and `effortLevel` on exact resume too, with no forking flags. The
gateway stays host-managed; status shows `gateway_settings_warning` with a `/model` or `/effort` hint when its
observed model or effort differs from the mode. Init output names the mode and `/agent-room:mode advisors`.
`/agent-room:init` is the main init skill; `init-agents-space` stays as an alias. All settings are requests, not
proof that a model used them.

## Patch 0.3.24: same-inbox wake-all fairness

Dispatch now selects up to 20 direct messages followed by up to 20 FYI messages per eligible
recipient per dispatch pass. FYI includes peer broadcast copies and admin relays. This lets a full direct
batch and its recipient's required wake-all notifications progress in the same pass while preserving FIFO
within each class. The selection bound is at most 40 per recipient or 160 across the four-member room. A
fake-native regression verifies that admin relays no longer consume the direct allowance.

## Patch 0.3.21: admin reply shape and the i-have-asd-ste100 dependency

Admin replies use the admin's eight-section shape: key-first bullets, a bold Conclusion line, a blank line,
then 0. Done, 1. InProgress, 2. Pending, 3. Questions, 4. Todos, 5. Backlog, 6. Risks, 7. AIIdeas. Installing
Agent Room in Claude Code also installs i-have-asd-ste100, which carries the full reply rules. The changes
below, made after 0.3.20, also ship in 0.3.21.

## Workspace changes after 0.3.20

New projects now initialize all four roster members by default. `--mode full` remains accepted as a
compatibility alias for the same roster. `send`, member-triggered notices and gateway admin relays
atomically enqueue a delivery for every other member; native dispatch begins when each queue is
available. Fanout copies carry an explicit FYI marker, while the direct recipient remains the only
owner of the request/task. Each dispatch pass selects up to 20 queued messages per eligible active recipient,
prioritizing direct requests and keeping FIFO within the direct and FYI classes. Selected recipient queues start
concurrently; one busy inbox cannot consume another member's allowance. Stopped or paused members retain
their queued messages. `wakes` reports enqueues, attempts, native results and processing ACKs
separately; it does not establish a read or expose model usage. New Claude worker sessions receive their
roster model and effort flags; Codex thread start/resume requests the roster model and each new turn
requests its model and effort. Existing Claude sessions resume without an override, and an already-running Codex turn
is not changed. The active Claude gateway remains host-managed. Full status separates requested settings
from a model reported by Claude `SessionStart`; absence of a reported model remains unknown. Fake-host
tests cover the request fields, but no live provider run verifies model availability, selection, token use
or cost.

Claude `sonnet`/`opus` are provider-dependent aliases to the latest family version, not fixed IDs; the
[Anthropic API mapping](https://docs.anthropic.com/en/docs/claude-code/model-config) documented on
2026-10-02 is Sonnet 5.5/Opus 5.5. Codex requests the exact IDs `gpt-6-luna` and `gpt-6.1-sol`, which
[Codex docs](https://developers.openai.com/codex/models) list with availability dependent on plan, client
and rollout. Codex documents [`xhigh`](https://developers.openai.com/codex/config-reference) as model-dependent.
Agent Room does not query the account catalog or silently fall back; requested settings remain distinct from
host-confirmed selection.

This source tree has local changes that are not in the current versioned ZIP. A matching Agent Room
peer header in a bound Claude `UserPromptSubmit` hook records `prompt_observed_at` and a
`native.prompt_envelope_observed` event on the latest attempt. The hook uses its `session_id` payload
plus the main owner's session or the worker's binding token and native session identity; it does not
require `AGENT_ROOM_SESSION_ID` to be injected into the hook process. Claude's hook receives submitted
prompt text but no authenticated peer-origin field, so this is text-observation evidence only: it
does not prove the supervisor sent the message, change `submitted`/`failed`/`unknown` delivery status,
clear recovery, or acknowledge processing. The recipient still reads the message and sends an ACK
after useful processing. No database schema change is required.

Room interruption marks any active native attempt `unknown`, even when a processing ACK exists. The
message remains `processed`; that ACK records useful message processing but does not prove the native
turn ended. No database schema change is required.

Structured CLI commands accept `--input` as an existing JSON file, `-` for stdin, or an inline JSON
object whose first non-whitespace character is `{`. For example:

```text

```

Shell quoting still applies to inline values; use shell-safe quoting or an existing file for text with
shell-sensitive characters. A file path beginning with `{` can be made unambiguous with a path prefix
such as `./`. This describes current source behavior, not the current ZIP.
Version/ZIP creation remains pending; this workspace note does not claim a released package.

## Patch 0.3.20: selective delivery context with explicit recovery

Task-free deliveries name `agent-room send --to MEMBER` for useful replies. Native final text
remains history, not a room reply. The footer follows the actual body, including operational notices;
ordinary conversation needs no task or fixed format and no unrelated status/inbox sweep.

Immediately before each dispatch, the supervisor checks for this recipient's `failed`/`unknown`
messages. A later delivery then points to all pending inbox pages and reconciliation before related
actions. This includes a failure earlier in the same dispatch batch. Processing ACKs or explicit
reconciliation/retry can clear that delivery state; no effect is retried automatically. Another
member's failed delivery does not force this member's sweep. The first failed/unknown dispatch to a
worker also queues one notice to main per unresolved failure episode. A dispatch failure to main
never creates another notice. This retains visibility when no later worker delivery arrives and
avoids a notice recursion. Start/resume still checks current state.

Fresh Claude-worker startup receives guidance through the native appendix. The hook does not duplicate
it for `source=startup`; resume, compaction and missing/unknown source receive identity and current
guidance. Native bindings and identity mismatch warnings remain. This is a conservative context
policy, not proof that native Claude restores every launch option or that models follow the guidance.
When identity or binding verification fails, the hook emits the warning without asserting membership.

Known raw room events, background task notifications and reserved native wrapper prefixes are excluded
from admin receipts and authority checks. Wrapper handling is defensive: a fixture that supplies
wrapped text is not evidence that the real hook receives it. Human text pasted with a reserved prefix
at the beginning is also rejected; write the admin request in your own words before the quote.
The current hook has no structured peer-origin field. Arbitrary unmarked cross-session text therefore
cannot be distinguished from human text at this ledger boundary; native permission controls and the
main's interpretation remain necessary. This patch does not establish universal human provenance.

Schema stays 3; custom room guides remain preserved. Older unconditional-read conventions may need
an explicit project-specific update before selective reading has an effect. Model tokens, tool-call
reduction, cooperation and speed require native evaluation; prompt bytes and offline checks alone
do not measure them.

## Patch 0.3.17: optional inbox previews

`inbox --compact` changes only the read projection. Each row replaces `body` and `detail` with
`body_preview` and `detail_preview`, using the existing bounded helper (1200 characters plus
` [truncated; read full record]` when longer; null detail stays null). All other message fields,
task staleness and current knowledge-reference metadata remain intact. `{items,next_after}`,
recipient binding, ordering, limits and `--pending` filtering stay the same. Plain `inbox` and
`inbox --pending` retain their complete row shapes and text. This is a text prefix, not a semantic
summary or total-response byte budget; context metadata is not truncated.

Each preview includes `agent-room inbox --after SEQ_MINUS_ONE --limit 1` as `read_command`.
Messages are append-only, with immutable sequence/recipient/body. Under the same member binding,
the command rereads that exact row and current metadata. It deliberately omits `--pending` and
`--compact` so ACK between reads cannot skip the target. Confirm the returned ID; the command is
recipient-scoped, not a capability to read another member's messages. Status, task state and linked
knowledge can change between reads, which are independent transactions.

Keep filters while following `next_after` and restart each new pending sweep at `--after 0`.
Previews are for orientation; process complete content from native delivery or a full reread and
reconcile current context before acting/ACK. Reading does not acknowledge, persist a read cursor,
retry dispatch or create work. Native delivery keeps the full body. Agents choose this view when
useful; startup pointers and recurring native prompts do not require it. There are no new schema,
module, provider call, scheduler or conversation rules.

Measured synthetic fixtures show smaller one-response output for long bodies, but short messages
and preview followed by every full reread produce more output. These byte counts do not prove lower
total tokens, provider cost, or native model adoption. Existing room files stay preserved at re-init;
use `guide cli` for the invoked plugin's current instructions.

## Patch 0.3.11: recall ordinary room conversations

`history --query TEXT` filters the selected `--kind` before pagination. All whitespace-separated
terms must occur as literal Unicode case-insensitive substrings in `body` for messages/prompts,
or the stored `data` JSON text for events. JSON keys and escapes are searchable as stored; event
kind, message sender/recipient/context and prompt origin are not part of matching. This is lexical
selection, not semantic ranking. The query is at most 200 characters. Missing, empty or whitespace
queries retain the prior full-history result. Invalid query length exits 1 with the normal error
envelope; invalid parser choices retain exit 2. No additional member binding is required.

The existing `{items,next_after}` response and complete row shapes remain: bodies/data are not
summarized, truncated or decoded, and origin/status/context/IDs/cursors are preserved. Rows retain
insertion order. The default limit is 50, maximum 200, and `after >= 0`. Filtering occurs before
limit+1 lookahead, so a null next_after means no further match in that read. Keep kind/query across
pages; each page is a fresh transaction, not a cross-page snapshot. Start a new search at after=0.
Rows can still be large. Selective recall reduces returned unrelated text on measured queries;
it does not establish lower total model tokens or faster scanning of large ledgers.

A connection-local SQLite function implements the filter in the existing history read path.
Queries never become SQL code. No index, persisted cache, schema change, new command, background
turn or native/provider call is added. Only the selected project's existing ledger is read;
there is no personal transcript or cross-project search. Reads do not acknowledge messages,
retry dispatch, account prompts, project Markdown or change task/knowledge state. Failed/unknown
messages remain visible with their actual status. Match text is not proof of processing or authority.

A matching conversation row may omit nearby disagreement or later correction. The learning guide
suggests reading surrounding unfiltered history/current records and preserving original IDs as
evidence before saving a lesson or tentative preference. Existing guidance on original admin
receipts and current authority still applies. Members choose whether a conversation deserves a
record; recall does not require every exchange to become a task, note or knowledge entry.

Schema stays 3. Stop the room and old controllers, update the plugin, run `init --no-start`, then
reopen. Custom room guides are preserved; `guide learning` and `guide cli` expose current references.

## Patch 0.3.7: share lessons with visible revisions

`send --knowledge K-ID` adds an optional lesson reference to an ordinary peer message. The
message still requires a recipient and nonempty free-form body; `--task` remains optional.
The existing identity, queue, transport, ACK and permission contracts apply. Only explicit
links are interpreted; a lesson ID mentioned in prose remains ordinary text.

In the send transaction, the store resolves the project-local knowledge ID and persists
`context.knowledge = {id, version}` beside existing task context. The captured version is the
version current at queue time; it does not certify what the sender previously read. Unknown
IDs fail before insertion. A retired lesson can be linked to discuss a correction. No lesson
body, sources, tags or limits are copied into the message context; use the full read command.

For a repeated message `--id`, sender/recipient/task/body and linked knowledge ID must match.
The original message and its captured version are returned even if the lesson has since changed.
Adding, removing or changing the link on that ID is a conflict. A new discussion intent uses a
new message ID. The existing transaction serializes duplicate sends; no separate queue is added.

Inbox reads add `knowledge_reference` only to linked messages: `id`, `queued_version`,
`current_version`, `changed`, current `state`, `basis`, `title`, `read_command` and `history_command`.
Each read compares with the current record. `changed` means a revision difference, not a verdict
on truth or applicability. An unchanged lesson may already be retired. Task `stale` keeps its
separate task-version meaning. The read leaves original message text/context/status unchanged
and does not acknowledge, retry, broadcast, create work or invoke a model.

At native dispatch, `begin_attempt` resolves the reference inside the attempt transaction.
That reference is persisted with the attempt and sent in the Claude/Codex text payload as
advisory metadata. A lookup failure rolls back the dispatch claim and attempt. Later knowledge
edits do not rewrite that observation; fresh inbox reads show newer revisions. Current state
can change again after any read, so recipients still read the full record and sources before reuse.
Neither a reference nor `basis=admin` is task authority, permission, receipt or proof of learning.

Schema stays 3; existing context/attempt JSON holds the optional fields. Legacy unlinked messages
retain their shape. Knowledge writes remain silent; members choose useful recipients and follow-up.
There is no scheduler, required debate, automatic broadcast or new model loop. Stop the room and
old controllers before upgrading; update, run `init --no-start`, then reopen. Custom guides remain
preserved; `guide learning` reads the installed CLI's current reference.

snapshot; start every new search at `--after 0` so revised/reopened earlier notes are reconsidered.
Search only current revisions; use `note history ID` for recorded past conclusions.

Search and `note list` read the notes ledger directly without computing task reviews, touching
source files, projecting Markdown, acknowledging messages or starting native work. They need
no member binding, consistent with other public local room reads. Full `note list` retains its

## Patch 0.3.4: autonomous follow-up on advisory ideas

`note resolve ID --expected-version N --input FILE` accepts a member conclusion on an ordinary
advisory question/proposal from its author or main. `answer` must be nonblank. A question can be
answered, reopened or superseded; a proposal can remain open, be rejected/withdrawn or superseded.
An optional `superseded_by` requires state `superseded` and must name another existing note;
reopening clears that pointer from the current revision. Original body/author are preserved;
the server records `resolution: {actor, basis: "peer" | "admin"}` for each resolution.

Main plus a valid original admin receipt in `source` remain required when approving a proposal,
editing a decision or previously approved/admin-sourced note, touching an existing task binding
(including legacy open proposals), or supplying `source`/`condition_evidence`. Peer conclusions
cannot change assignments, task contracts, native permissions or review receipts. A peer cannot
edit another author's note; send disagreement/counterevidence to the author. Main may coordinate
an ordinary advisory conclusion without claiming admin provenance. Creation with an admin source
also requires main and a valid receipt; callers cannot supply server-owned `resolution` metadata.

Each note write and its full `note.revised` event commit in the same SQLite transaction as existing
notifications. Version conflicts or event-write failures leave no partial note/notice/history write.
`note history ID [--after CURSOR] [--limit N]` is read-only, default 8, max 50. It returns recorded
revisions and current version/state. History before this feature can be absent; no backfill or
invented reconstruction is performed. Knowledge and notes reuse the same revision reader; their
event kinds stay separate and the knowledge history response retains its advisory rule.

The existing queue notifies main, the author and other linked task owners when notes change.
Duplicate task links produce one task notice; a recipient of a task notice gets no extra general
notice for the same change. Distinct linked tasks retain their own context notices. Notification
states keep the existing saved/submitted/processed meanings; reads and ACKs do not generate replies.
No separate timer, reflection turn, automatic code edit or wake mechanism is added. Native members
choose useful discussions, lessons and proposals within authorized work; the plugin preserves and

## Patch 0.3.2: compact status and package verification

`status --compact` is an opt-in read-only projection of current status. All unfinished task
identities remain visible; done/cancelled tasks are counted by state. Open questions/proposals
and approved decisions have bounded previews and exact read commands; other notes are counted.
`task list --all`, `note list` and plain `status` retain full history. Task context remains the
required full read before acting. Unknown native attempts and stale reviews stay explicit.

The projection keeps original unaccounted admin text, native approvals, claims, operational member
state and advisory attention unchanged. Requested/observed model settings are available in full
`status`; the compact response points to that read so they do not consume the frozen context budget.
It adds no cache, acknowledgement, wake-up or data migration.
New startup/message guidance uses the compact view; re-init still preserves custom room guides.
Status size can still grow with genuinely active work, pending admin text or approvals. This is
selective context, not a fixed global token cap.

`verify-package ARCHIVE` works before room/identity lookup and needs no native executables.
It reads ZIP entries and checks exact manifest/payload names, SHA-256, canonical paths, duplicate
ZIP/JSON keys, regular-file metadata, declared size/count bounds and decoded size agreement.
Limits: 256 entries, 16 MiB declared per entry, 64 MiB total declared; no extraction/execution.
Empty payload sets are valid. The manifest version is returned; no current-version match is required.
This is integrity checking against an archive's own manifest, not publisher authentication.

With `--json`, success is one `{ok:true,data:{version,files_checked}}` object, exit 0.
Archive/I/O/validation failures use `{ok:false,error:{code:"package",message:...}}`, exit 1.
Invalid arguments keep the CLI's exit 2 behavior. No room or files are created by verification.

Queued, dispatching, submitted, accepted, failed and unknown messages remain visible. Bodies,

## 0.3.0: shared learning and selective context

This increment adds one `knowledge` table to the existing SQLite ledger. Native agents choose
when to extract and use knowledge during their ordinary turns; the plugin adds no model loop,
reflection timer, mandatory debate, embeddings service or automatic broadcast. Conversation,
task assignment, source-bound review and native permissions retain their existing boundaries.

`knowledge add --input FILE` requires nonempty `title`, `body`, and at least one nonempty
`evidence` string. Optional `tags` are nonempty strings; `applies_when` and `limits` are free-form
text. Since 0.3.8, content lengths and source/tag counts are writing guidance rather than validation
quotas; search and message references retain bounded previews. `basis` is `inferred` by default,
`observed` for a member-reported observation, or `admin` for main's interpretation of a real admin
receipt in `source`. Structural validation is not semantic verification. Evidence pointers are
not fetched or certified by the store. An admin receipt proves a recorded prompt exists, not
that the saved interpretation matches it. Knowledge never supplies authority to tasks/approvals.

All bound members may add/revise ordinary records. An admin-basis record can only be created
or revised by main with an original receipt. To replace an inaccurate admin statement with a
hypothesis, main retires it and records the inference separately. `update ID --expected-version N`
uses the same transaction/version discipline as tasks. Author and latest editor are distinct;
each successful revision and its history commit together. A version conflict requires rereading.
Intake accounting may refer to a knowledge ID without converting that knowledge into a decision.

`knowledge search 'terms'` searches only this project's current records, using Unicode casefold
and literal AND matching across title/body/tags/evidence/applicability/limits. It returns bounded
previews, IDs and read commands, default 8, max 50, with `next_after` pagination. There is no
semantic ranking or global/native-memory fallback. `show ID` returns the full current record.
`history ID` returns explicit historical revisions and the current version/state. Retiring via
`state=retired` excludes the record from default search immediately; explicit history/show and
`--include-retired` still expose it. Retirement is not erasure; sources/backups and native agent
context are not scrubbed. Keep secrets and unrelated personal data out of this shared store.

Native dispatch now attaches a stateless `detail=summary` task context: task version, contract,
owner, authority, state, bounded title/next action, current review submission/source digest,
checkpoint ID and unknown-effect count, reconciliation warnings, recent attempt IDs/states,
and up to 10 blocked dependency IDs with the full count. It tells the recipient to read
`task context TASK_ID` before acting. Full `task context` remains available with its prior
bounded recovery/attention/evidence contract. Attempts persist the digest of the delivered
summary. No session cache assumes a model remembers previously delivered text.

`--json` now emits compact JSON on one line; parsed result fields are unchanged. Ordinary
human-facing command output remains indented. The shared collaboration/learning prompt lives
in `resources/collaboration-guidance.md`, used by Claude SessionStart and native worker startup
and resume. More extensive guidance is retrieved from the room only when needed. Existing
custom room guides remain untouched; re-init after migration adds the new learning guide.

Payload character/byte comparisons establish reduced repeated input in specific fixtures,
not lower total tokens/cost or better creativity. Extra context retrieval and learning may
cost tokens. Actual extraction, recall quality, preference interpretation and self-improvement
benefit need a separately authorized native workload; offline storage tests cannot prove them.

## Patch 0.2.3: read-only attention

`agent-room status` and `agent-room task context TASK_ID` now include an additive
`attention` field: `advisory: true` and `by_member`, keyed by the four fixed member identities.
Status shows the room's unfinished work; task context shows only the requested task.
Entries are derived inside the same database read transaction as the surrounding context,
using its current review/source checks. No reminder records, schedule or second work queue
are created. Schema stays at 2 and no database migration is needed.

Each entry includes `task`, a bounded `title`, task `state`, `reason`, `episode`, `blockers`
and `read_commands`. Review-state entries also include the current `review` result and its
submission/receipt pointers. Reasons and recipients:

- `unfinished_task`: current owner of ready/running work, or submitted work with no peer policy.
- `blocked_task`: owner, with the explicit blocker when recorded.
- `pending_review`: current reviewer, for the current readable submission only.
- `review_changes_requested`, `review_blocked`, `review_stale`: owner, to inspect the receipt
  or reconcile the changed source/contract before deciding how to proceed.
- `review_approved`: main, which owns completion of peer-required tasks.
- Done/cancelled tasks produce no entry. There is at most one entry per unfinished task.

An entry's identity is `(member, task, reason, episode)`. Task episodes use `contract:N`;
review episodes use the current submission ID. Checkpoint/progress version bumps do not
create a new episode. Reassignment and resubmission are reflected on the next read.
Blockers describe declared blocked state, incomplete dependencies and unsatisfied bound
decisions, including legacy proposal bindings. Claim conflicts and native permissions retain
their existing checks; an empty blocker list is not an execution authorization.

Attention reads do not mutate SQLite, project views, task versions, source files, message
ACKs, review receipts or native processes. An ACK does not clear pending work. Free questions,
tentative proposals and unacknowledged messages alone create no attention entries. Members
remain free to converse or offer help without an entry or task ID. No urgency, deadline or
mandatory response order is inferred. The view includes saved assignments even when their
member or room is stopped; use the normal mode/liveness fields to interpret availability.

Task-context size limits still apply: previews and omitted blockers are marked explicitly,
and record commands remain available. This increment implements the pull view from the
0.2.2 pilot design. Reminder footers, question pins, seen/defer/dismiss state and timers are
not implemented. Existing custom room guides remain preserved on re-init; the updated
plugin status skill and context fields are available with the new package.

## Patch 0.2.2: proactive collaboration and recovery

The room encourages direct questions, brainstorming, constructive disagreement, reminders
and offers of help. Ordinary discussion needs no task ID, note record, mandatory message
format or fixed number of rounds. Main retains admin intent and integration ownership;
expertise guides contributions without restricting who can raise a useful idea.

The shared startup guidance is injected into Claude SessionStart and native worker role
instructions, including Codex thread resume. Fresh scaffolds include a collaboration guide.
These are model instructions, not evidence that every model will follow the intended behavior.

New open proposals are advisory even when linked to tasks. Creating, rejecting or superseding
an unbound proposal leaves task version, contract revision, decisions and review validity
unchanged. Main approval binds a linked proposal, increments the task contract and invalidates
an earlier review; conditions still block execution until their evidence is recorded.
Questions remain advisory. Existing bound notes, including open/rejected proposals written
by <=0.2.1, stay bound until main explicitly resolves or supersedes them with an admin receipt.
An already binding proposal reopened/rejected still gates work; superseding removes that binding.
No history is rewritten and no schema migration is required.

Dispatch selects up to 20 queued messages per eligible active recipient per pass. It selects
that recipient's direct messages before FYI copies and preserves FIFO within each class. The
limit is per inbox, not room-wide: one busy recipient cannot consume another member's dispatch
allowance. Inactive, stopped, failed or native-input/permission-waiting members do not consume
the selection budget. Their messages remain queued. This is not a timeout guarantee for a slow
native transport or a new conversation quota.

After native workers resume, the store queues notices for unfinished worker-owned tasks and
current pending reviews, including reviews assigned to main. A queued message for the same
recipient/task at the current task version supplies the wakeup and prevents a duplicate.
Unrelated messages and older task versions do not suppress a needed notice. Review wakes
require state `review` and current review status `pending`; approved, changes-requested,
blocked, stale and terminal work does not create another reviewer request. The notice names
the current submission and asks for reconciliation. Old attempts remain unknown where their
outcomes were unknown; the old native operation is not replayed.

Historical 0.2.2 installation instructions (use the current upgrade section for 0.3.0):
before a schema-2 upgrade, stop the room with the old plugin and close its old controllers.
Install 0.2.2, then run its `bin/agent-room --project PROJECT init --no-start` and reopen/start.
Init adds the collaboration guide and updates managed AGENTS/CLAUDE pointers while preserving
existing room templates/custom instructions. Startup guidance also reaches existing rooms;
review custom instructions yourself if they impose a different conversation policy.
Use one plugin version per room. Downgrading to <=0.2.1 restores its proposal-binding behavior;
schema compatibility alone does not preserve the new advisory semantics.

## Review contract

Main creates tasks with `review_policy: "none"` (compatibility default) or `"peer_required"`.
Peer-required tasks need an explicit active `reviewer` different from the owner. Main changes
policy/reviewer through the existing admin-source boundary. Existing authorizations remain in force.

1. Author finishes the assigned work/checks, then `task submit` with current expected version,
   nonempty summary/evidence and 1..256 individual project paths.
2. Store computes a source snapshot and immutable submission digest, retains author/contract/
   decisions/attempt links, enters review and releases the author's claim atomically.
3. Assigned peer inspects `submission show`, files, acceptance and evidence; `review record`
   must supply the exact digest. Source/contract/owner/decision/dependency/evidence changes invalidate the receipt.
4. Main can set a peer-required task to done only with a current approved receipt, evidence and
   satisfied dependencies/decisions. Task version checks still reject concurrent stale updates.

CLI operations:

```text
agent-room task create --input task.json
agent-room task submit T-ID --expected-version N --input submission.json
agent-room submission show S-ID
agent-room review record S-ID --input review.json
agent-room review show R-ID
agent-room task update T-ID --expected-version N --input done.json
```

Example fields added to a normal task: `"review_policy":"peer_required","reviewer":"CODEX_EXPERT"`
when CLAUDE_01 is the owner. Submission:

```json
{"paths":["src/example.py","reviews/checks.md"],"summary":"Implemented the assigned behavior","evidence":["Exact test command, outcome and evidence path"]}
```

Review:

```json
{"source_digest":"DIGEST_FROM_SUBMISSION_SHOW","verdict":"approve","summary":"Inspected source and acceptance checks","findings":[],"evidence":["Independent check and observed result"]}
```

Verdicts: `approve`, `changes_requested`, `blocked`. Approve requires no unresolved findings;
changes_requested requires at least one finding. Finding fields: nonempty `summary`, `severity`
(`high`, `medium`, `low`), optional submitted `path` and positive `line`. Identical receipt retries
are idempotent; conflicting receipts cannot overwrite history. After corrections or a resolved
blocker, the author creates a new submission. Its previous_submission pointer and `submission show`'s
review_receipts preserve access to earlier findings. To edit again, move to ready and acquire a claim first.

Only declared paths are fingerprinted, including recorded absence for deletions. At least one
regular source/report file must exist; deletion-only work should include its review/check report.
Directories, symlinks and runtime paths are rejected. The author/reviewer/main still judge whether
the declared review set and evidence cover acceptance. This is a coordination contract among trusted
local agents, not proof of all filesystem effects, an OS sandbox, or an automatic test runner.
Legacy `snapshot` and evidence-only completion remain available for policy none.

## Checkpoints and current context

```text
agent-room task checkpoint T-ID --expected-version N --input checkpoint.json
agent-room checkpoint show C-ID
agent-room task context T-ID
```

```json
{"summary":"Reached an inspectable boundary","last_safe_action":"Saved local patch and ran unit checks","unknown_effects":[],"next":"Ask the assigned reviewer to inspect submission","paths":["src/example.py"]}
```

Checkpoint records are immutable and sequenced per task. They bind owner, task contract, decisions,
native ID, generation and source snapshot. Concurrent/stale updates fail. `task context` includes
current scope/authority/acceptance, dependencies, decisions, review status and recent attempts.
Changed owner/session/generation/contract/source produces explicit reconciliation reasons.
Unknown effects stay visible; resuming never grants permission to replay them.

Context is bounded to roughly 12k characters plus its digest. Field previews and an oversized pack
are explicitly marked as truncated, with CLI pointers to complete task/submission/checkpoint/attempt
records. Native histories remain under each harness. Dispatch attaches a fresh pack for task-linked
messages; saved/native context can still become old, so recipients read current state before acting.
An old text checkpoint remains available until the owner adopts the structured command.

## Attempts and progress

Each dispatch writes an E-ID before sending. Its message/task/member/generation/native ID, observed
turn ID and native state remain separate from message processing and task completion.

```text
agent-room attempt list --task T-ID --after 0 --limit 50
agent-room attempt show E-ID
agent-room history --kind events --after 0 --limit 50
```

Codex agent-message output is retained in native event records; attempts reference event sequence IDs.
`output_state` distinguishes received nonempty output, empty output and output not observed. A native
completed/failed/interrupted turn remains its actual state and never closes a task. Multiple steered
messages can share one turn/output; the record does not prove independent work for each task.

Claude inbox submissions expose no native turn/output receipt. Those fields remain unknown. A
`prompt_observed_at` attempt field records that matching message text reached the bound
`UserPromptSubmit` hook. The hook validates its payload session against the bound owner or worker
binding/native session, because `AGENT_ROOM_SESSION_ID` is not guaranteed in the hook process. This
is based on prompt text, not authenticated native origin; it does not change delivery status or count
as an ACK. Explicit ACK/review/checkpoint evidence is separate. If interruption occurs before a
confirmed native turn result, the message may remain `processed` while the attempt becomes `unknown`:
the ACK is preserved but does not prove that the native turn completed. Explicit retry requires the
existing main reconciliation/source contract and creates a new attempt. No automatic replay is added.

Status exposes review_status, missing_evidence, latest_attempt, last_progress and unprocessed_messages.
Status/context/read commands make no model calls, spawn no workers and do not repair room state.
No model identity, token usage or billing estimate is invented from configuration.

## Upgrade and recovery

Schema 1 and 2 rooms require an explicit offline migration. Fresh rooms start at schema 3.

1. Use the compatible old plugin to stop the room and close old controllers. Confirm worker cleanup.
2. Update the plugin, then run `bin/agent-room --project PROJECT migrate` as operator/main.
3. The command locks control/supervision, rejects live workers or a running room, and makes a consistent
   SQLite backup under `agents_space/.runtime/backups/schema-N-UUID.sqlite3` before schema changes.
4. A transactional failure leaves the prior schema intact and retains the backup. Re-running after success
   reports already current. Native IDs, tasks, decisions, claims and messages are preserved. Schema-1 tasks
   receive policy none; schema-2 records are unchanged. The migration invents no reviews, checkpoints or native attempts.
5. Run `init --no-start` to add the new learning/evidence guides, then reopen/start normally. Existing customized
   templates are preserved; the installed CLI and new guide document the new operations.

Earlier readers reject schema 3. A rollback requires a stopped room, retaining the current database,
and an operator restoring the returned backup with the old plugin. That discards post-migration state;
the tool does not perform an automatic downgrade or destructive restoration. Migration never changes
native credentials, trust, model or permission settings. Doctor/status do not migrate implicitly.
